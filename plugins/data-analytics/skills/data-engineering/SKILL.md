# 数据工程

管道是生产系统，但它的故障是无声的。服务挂了会有人被叫醒；管道坏了却会产出看似合理的数字，人们据此行动一整周。

这里讲的是数据的移动和转换。Schema 和语义属于 `data-analytics:data-modeling`，策略和治理属于 `data-analytics:data-governance`。

## 原始数据原样落地，转换放在下游

保留一份源数据的不可变副本，完全按接收时的样子存储。转换逻辑迟早会出错，而原始数据让你能重新处理，而不是向可能已经没有这份数据的源重新请求。

业务逻辑放在下游，那里可见、可测试，不要埋在摄取层里。例外是隐私所需的转换——最小化、假名化、删除你无权保留的字段——这些必须在摄取时做，因为原始存储才是义务的附着点。参见 `legal-risk:privacy-and-data-protection`。

## 幂等性才是关键属性

每条管道都会被重跑：故障后、修复后、迟到的修正到达后。重跑导致重复计数比故障更糟，因为它会无声地产出错误答案。

在目标端设计精确一次的效果——确定性键、合并而非盲目追加、分区覆盖。这样重跑就是安全的，恢复也不再令人恐惧。

## 迟到、重复和乱序数据

真实数据源三种都会出现。每条管道都要明确决定：事件迟到多久仍被接受，窗口关闭后到达的事件怎么处理，重复数据如何识别。

区分**事件时间**和**处理时间**，按事件时间分区。基于到达时间的聚合，只要投递延迟，就会无声地把昨天的活动算到今天。

## 测试数据，不只是测试代码

对转换逻辑做单元测试只能捕获一类错误。大部分损害来自有效但错误的数据。在管道中对数据本身做断言，并且大声失败：

- 行数在预期范围内，而不仅仅是非零。
- 键的唯一性，以及跨 join 的引用完整性。
- 新鲜度——最新记录足够新，才有意义。
- 重要列的分布偏移。

无声失败比大声失败更糟。宁可停掉管道，也不要发布你不信任的数据。

## 工具

数据仓库和湖仓：Snowflake、BigQuery、Databricks、Redshift，小规模场景用 Postgres 或 DuckDB，以及类似工具。

摄取：Fivetran、Airbyte、Stitch 等。转换：dbt、SQLMesh。编排：Airflow、Dagster、Prefect 等。

摄取用买的，转换自己建。连接器维护的投入，对你的团队来说毫无回报。

## 绝不

- 因业务原因在摄取时转换并丢弃原始副本。
- 构建重跑会重复计数的管道。
- 事件时间可用时却按处理时间聚合。
- 让管道无声失败，把过期数据当作当前数据发布。
