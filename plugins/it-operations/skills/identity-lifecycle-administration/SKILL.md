# 身份生命周期管理

这里是执行层面：在人员入职、转岗和离职时创建、变更和移除权限。
**策略——某个角色应被授予什么权限，以及最小权限原则——属于
`security:access-and-identity` 的范畴。** 本技能执行策略所定义的流程，而两者之间的
差距正是大多数权限问题的所在。

## 入职

按角色配置权限，而非复制同事。复制是权限累积的最大单一来源：它会继承那个人
积累的一切，包括本不该拥有的权限，并将其无限传播下去。

为常见场景定义基于角色的权限包，让标准入职只需一次操作，将权限包之外的一切
视为需要审批的例外。例外没问题；未记录的例外不行。

将权限配置的时间安排在入职日期之前完成——通过
`people:onboarding-and-offboarding` 协调。

## 转岗是最被忽视的场景

离职会得到关注，因为有人要走了。转岗不会，于是权限不断累积：在三个部门工作过
的人拥有全部三个部门的权限，而前两个从来没人移除。

将角色变更视为**撤销并重新配置**，而非追加。这是大多数组织中可用的最高价值
修复，却几乎总被跳过，因为人还在，表面上一切正常。

## 离职，彻底处理

在约定时间及时禁用账户，然后执行一份清单，覆盖到目录之外的系统：未接入单点
登录的系统、本地账户、该人员知道的共享凭据、其创建的 API 密钥和令牌、用个人
账号采购的外部服务，以及任何邮件或日历委派。

缺口几乎总是身份管理触及不到的系统。明确维护这些系统的清单，而不是在审计时
才发现。

只要存在任何调查或法律保留的可能，就保留而非删除——删除不可逆，有时代价
极高。

## 重新认证，并据此行动

定期由系统所有者确认谁仍应拥有权限。只有未响应默认移除时才值得做；如果未响应
意味着保留，重新认证就变成走过场，认证的是现状本身。

专门排查孤儿账户——没有所有者的账户、无人认领的服务账户，以及数月未使用但
仍然有效的凭据。

## 来源

本技能中的 `references/sources.md` 列出了解决此处问题的外部权威来源——每个来源
在什么方面具有权威性，以及你可以如何使用它。在回答其涵盖的任何问题之前先查阅
它们，并引用你所使用的来源。大多数可免费阅读但不可免费复制；每个来源的使用
说明具有约束力。

## 工具

目录和 SSO：Microsoft Entra ID、Okta、Google Workspace、JumpCloud 等。

HRIS 作为触发源：Workday、BambooHR、Rippling、HiBob、Gusto、ADP 等。身份应
跟随 HRIS 记录，而非单独的一份在职人员名单。

只要应用支持，配置就通过 SCIM 运行。不支持的，入职-转岗-离职步骤就是手动的，
应放在工单模板里，而不是某人的脑子里。

## 绝不

- 通过复制现有用户来配置权限。
- 角色变更时只添加权限而不移除旧的。
- 目录账户被禁用就认为离职人员已完成权限回收。
- 在未响应意味着保留的情况下运行重新认证。
