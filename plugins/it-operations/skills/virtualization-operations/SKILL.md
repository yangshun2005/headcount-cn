# 虚拟化运维

虚拟化是大多数基础设施问题实际所在的层，也是大多数监控视而不见的层。客户机报告 CPU 健康，却在争抢一个它永远拿不到的核心。常见的错误是向上诊断——深入应用——而瓶颈其实在下面两层的主机。

## 整合比是决策，不是结果

每个集群都有虚拟资源与物理资源的比值，而大多数组织是发现这个比值，而非选择它。内存和 CPU 超配是正常且正确的；问题在于超配多少，以及峰值而非平均值时会发生什么。

有两个数字需要时刻掌握：集群当前的运行量，以及少一台主机时的运行量。如果失去单台主机就超出容量，那这个集群只在纸面上能扛住硬件故障，实际不能。按 N-1 规划，并把备用容量明列在预算中，否则第一个被砍掉的就是让设计成立的那份余量。

内存通常是真正的上限，而非 CPU。核心可以优雅地超配；内存不行。

## 蔓延是披着基础设施外衣的生命周期问题

VM 创建极其容易，删除却在人情上很难。没人记得这台机器是干什么的，于是它留着——消耗许可、备份容量、补丁工作，以及无人审查的攻击面。

解决办法是在创建时记录归属，而非每年清理一次。每台 VM 在构建前都要有指定的所有者和审查日期。任何说不出所有者的都是退役候选，退役路径是：关机、等待一段确定的时间、然后删除。先关机把不可逆的决定变成可逆的，并会带来那通告诉你这台机器做什么的电话。

模板和黄金镜像让整个环境保持一致。从模板开始的构建比某人手工拼装的构建漂移更少，而漂移正是让补丁变得不可预测的原因——这套配置基线所支撑的内容见 `it-operations:systems-administration`。

## 快照不是备份，旧快照会导致故障

快照是针对磁盘的变更日志，会一直增长直到被合并。放任不管，它会填满数据存储，并拖垮共享该存储的所有 VM，这比快照原本要防范的问题严重得多。

把它们当作针对特定变更的短期工具：在风险升级前拍一个，当天就合并，并对任何超过你所设阈值的快照告警。它们不是保留机制，也扛不住存储故障——真正的恢复属于 `it-operations:backup-and-recovery`。

## 实时迁移是维护能力，不是弹性能力

在主机之间迁移运行中的工作负载，是让虚拟机监控程序无需维护窗口即可打补丁的关键，仅凭这一点就足以证明其价值。它并不能防范主机突然故障——那是另一台主机上的重启，停机时间以启动时间计。

要清楚哪些工作负载能承受这种重启，哪些不能。不能的那些需要在客户机内部做集群，虚拟化它们并不能免除这一要求。

## 许可按你配置的量计费，而非你使用的量

虚拟机监控程序和客户机许可通常按物理核心或插槽计价，这意味着整合决策同时也是许可决策，增加主机在许可上的花费可能超过硬件。有些厂商对工作负载可能迁移到的集群中所有核心计费，而非它实际运行的那一个——这把一个可用性设置变成了账单。

在采购硬件前先建模许可成本，集群扩展时再核对一次。`it-operations:it-asset-management` 负责授权记录；本技能负责了解哪些架构选择会改变它们。

## 与云的边界在哪里

并非一切都应在本地虚拟化，也并非一切都应迁移。诚实的检验标准不是每 VM 成本——而是工作负载的需求是平稳还是波动。平稳、可预测的负载在自有硬件上运行更便宜。波动或季节性的负载才是云弹性真正的用武之地。

混合是正常的终态，而非过渡期的尴尬。让它痛苦的是运行两套运营模式、两套习惯，所以要有意识地决定由哪一方掌管身份、监控和备份，而不是让两边各答各的。

## 绝不

- 配置没有所有者、没有生命周期、没有退役触发条件的客户机。
- 规划集群时不留出维护期间失去一个节点的余量。
- 在检查客户机本身是否行为异常之前就扩充其资源。过度配置会掩盖缺陷并吞噬整合比。
- 为了逃避一个你尚未在本地诊断清楚的容量问题而把工作负载迁移到云。
