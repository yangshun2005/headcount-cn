# 云管理

企业云是买来的，不是设计出来的。有人需要某个工具，报销了事，它便进入了资产清单，既无审查，也无责任人，更无退出路径。典型的失败不是设计糟糕——而是多年后靠一张张发票才发现这些资产的存在。

这里讲的是业务运行所依赖的云。至于产品构建所依赖的云——环境、基础设施即代码、扩缩容、区域故障——参见 `technology:cloud-infrastructure`。两者规则不同，边界值得划清。

## 在需要之前先规划好租户结构

订阅与账户结构决定了日后能拆分什么：计费、访问、策略和影响范围。事后改造意味着迁移在线工作负载，所以最省事的时机就是一开始。

可行的默认做法是按需要独立计费、独立治理或独立承担损失的对象来拆分——生产环境的企业服务、非生产环境，以及任何有独立合规义务的部分。不要按团队划分订阅；团队会重组，而结构比团队活得久。

创建时就打上责任人、成本中心和环境的标签，并用策略而非文档来强制执行。未打标签的资源一个季度内就会变成无法归属的支出，而且没人会主动认领。

## SaaS 资产是无人管理的那部分

大多数公司都大幅低估了自己的应用数量，因为他们知道的应用是 IT 买的，其余则是所有人各自买的。真正有效的发现手段是财务层面的，而非技术层面的：报销单、公司信用卡账单，以及身份提供商的登录日志。网络监控能发现的比会计系统少。

每个应用都需要指定业务责任人、续约日期和数据分类。没有责任人，续约时无人可问。没有续约日期，谈判只能发生在自动续约之后。没有分类，供应商被攻破时没人知道适用哪些数据泄露通知义务。

存储客户或员工数据的应用，应纳入 `legal-risk:privacy-and-data-protection` 所述的审查流程；离职员工对它的访问权限属于 `it-operations:identity-lifecycle-administration` 的职责范围——而该流程无法为一个它根本不知道存在的应用解决问题。

## 身份就是边界，所以要当作基础设施来对待

资产一旦上云，网络位置就保护不了任何东西，身份提供商是唯一一致的控制点。因此单点登录不是便利功能，而是让权限回收能在一处完成、而非四十处的原因。

实用规则是：拒绝无法联邦认证的应用，或者明知如此仍接受，但记录手动下线步骤。对 SSO 额外收费的供应商，收的是安全基线的钱，这笔成本应计入采购决策，而不是事后才发现。

条件访问、MFA 和特权角色激活是值得投入的控制措施。设计参见 `security:access-and-identity`；本技能负责在真实资产环境中运营它们。

## 云支出意外是结构性的

云账单会增长，因为系统里没有任何东西阻止它。资源创建很容易，没人会自掏腰包，消费在收到发票前不可见。

三个习惯能抓住大部分问题：在每个订阅上、工作负载落地前设置预算告警；每月审查变动最大的项目，而非整张账单；定期检查无人登录却仍在运行的资源。预留和承诺定价对稳定工作负载确实省钱，但那是对用量水平的押注——只在负载真正可预测时才承诺。

非生产环境在夜间和周末持续运行是最常见的单项浪费，按计划关停它没人会察觉。

## 责任共担比人们以为的范围要窄

云厂商只保证平台可用。几乎其他一切——配置、访问，多数情况下还包括数据本身——都归你。

最容易让组织栽跟头的是备份。大型 SaaS 套件能防自身的故障，但防不了用户删除邮箱，也防不了勒索软件通过同步扩散。保留策略不是备份，回收站不是恢复点。应在 `it-operations:backup-and-recovery` 下明确决定哪些数据需要独立保护，而不是想当然地以为厂商的持久性承诺能覆盖你的失误。

## 工具

平台：AWS、Microsoft Azure、Google Cloud 等。

基础设施即代码：Terraform、OpenTofu、Pulumi、Bicep、CloudFormation 等。

成本可见性：原生成本工具，或 CloudZero、Vantage、Finout 等。
护栏：AWS Control Tower、Azure Policy、Wiz 等。

控制台上无法用代码复现的改动，会变成你无法重建的故障。

## 绝不

- 购买无法联邦认证的应用却不记录手动下线步骤。
- 让资源在没有责任人标签和成本中心的情况下存在。
- 把厂商的保留策略当作备份。
- 按当前组织架构规划订阅结构。
