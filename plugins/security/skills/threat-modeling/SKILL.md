# 威胁建模

在设计阶段做，成本低，还能改变设计。上线后再做，只会产出一堆修复代价高昂的问题清单，所以时机本身就是大部分价值所在。

## 四个问题，按顺序来

**1. 我们在构建什么？** 画出真实的数据流图——不是组织架构图，也不是营销架构图。组件、组件之间流动的数据，以及每个存储的位置。如果没人画得出来，这本身就是第一个发现。

标出**信任边界**：数据从你控制的范围跨入你不控制的范围，或从一个权限级别跨入另一个权限级别的每一个点。几乎所有真实漏洞都位于边界上。

**2. 会出什么问题？** 逐个走查每条边界和每项资产。一组可用的提示：

- **仿冒** — 有人能冒充另一个用户、服务或系统吗？
- **篡改** — 数据在传输中、静态存储中或客户端上能被修改吗？
- **抵赖** — 有人能否认某个操作吗？我们能拿出证据反驳吗？
- **信息泄露** — 什么会泄露：给其他用户、给日志、给错误消息、给客户端打包产物？
- **拒绝服务** — 什么是无界的？上传、查询、重试、扇出。
- **权限提升** — 用户能触及属于其他租户、角色或账户的数据或操作吗？

比经典清单更能抓到真实 bug 的两条：**客户端强制了什么而服务端没有**，以及**第二次尝试会发生什么**——重放、竞态和重复提交。

**3. 我们打算怎么应对？** 对每个现实威胁：缓解、转移、规避或接受。接受是合理的；默默接受则不是。

按攻击者投入对比影响来排优先级，而不是按听起来多吓人。一个可轻易利用的租户隔离 bug，永远优先于一个理论上的时序攻击。

**4. 我们做得好吗？** 设计变化时重新检查模型。一个描述上个季度架构的威胁模型比没有还糟，因为它会带来虚假的信心。

## 范围界定

按功能或按边界建模，不要按系统建模。全系统模型太大，做不完，也太模糊，无法落地。

限定时间。和将要构建它的工程师一起，针对具体功能花一小时，胜过花一周产出一份没人看的文档。

## 绝不

- 按设计中的系统建模，而不是按实际构建的系统。要问实际交付了什么。
- 假设内部流量可信。正是这个假设把一个被攻陷的服务变成一场事故。
- 接受"框架会处理"而不检查它是否已配置为处理。
