# 安全架构审查

## 按此顺序审查

按此顺序投入注意力，能最先发现影响最大的问题。

**1. 身份验证。** 身份如何建立、会话如何表示、如何过期、密码重置和账户恢复时会发生什么。恢复流程通常是进入账户最薄弱的路径，也是审查最少的环节。

**2. 授权。** 最重要却最容易被忽视的一环。对每个端点和每个对象：谁被允许访问，检查在哪里执行？典型失败是在入口处检查，却没在对象本身上检查，导致任何已认证用户都能通过修改标识符访问任意记录。

多租户隔离要显式检查并通过测试验证，而不是靠阅读代码。假设请求中的每个标识符都受攻击者控制——因为事实如此。

**3. 数据。** 收集了什么、流向哪里、存储在哪里、谁能读取。日志、错误响应、分析载荷和客户端打包文件中的敏感数据——这四类都是常见发现。

**4. 输入与输出。** 不可信输入到达查询、模板、命令、反序列化器或服务器发起的 URL。用参数化而非转义。用允许列表而非拒绝列表做校验。

**5. 密钥。** 绝不放在源码、客户端打包文件或构建日志中。可轮换、按需限定范围，并有文档化的轮换路径且有人实际走过。

**6. 依赖项与供应链。** 引入了什么、如何锁定版本、更新如何审查，以及维护者账户被攻破会发生什么。提交锁定文件，构建可复现。

## 审查变更而非设计

关注：没有授权检查的新端点、新的外部输入、变更的身份验证或会话逻辑、新依赖项、任何涉及密码学的内容，以及任何扩大角色权限的内容。其余通常收益较低。

**绝不自己写密码学。** 使用经过验证的原语，对任何手写实现比较、令牌或签名的 diff 保持怀疑。

## 来源

本技能中的 `references/sources.md` 列出了解决此处问题的外部权威——每个权威的适用范围，以及你可以如何使用。在回答其覆盖的任何问题前先查阅，并引用你所使用的来源。大多数可免费阅读但不可免费复制；每条的使用说明具有约束力。

## 工具

- **SAST** 能低成本捕获某类缺陷，但会产生大量误报。要么调优，要么团队会学会忽略它——那比不运行更糟。
- **DAST** 和依赖扫描发现的是不同问题；两者都不能替代审查。
- **CI 和 pre-commit 中的密钥扫描**是单位投入价值最高的自动化。

目前的具体工具：SAST 用 Semgrep、CodeQL 或 SonarQube；依赖用 Snyk、Dependabot 或 Trivy；DAST 用 Burp Suite 或 OWASP ZAP；密钥用 gitleaks、TruffleHog 或 GitHub secret scanning——每类还有类似工具。

自动化是底线，不是审查。它发现已知模式，而非设计缺陷——而设计缺陷才是真正导致高昂事故的原因。

## 第三方集成

哪些数据离开、依据什么协议、拥有什么访问权限，以及对方被攻破会怎样。凭证按最小范围授予，优先使用短期令牌，并知道如何在不造成中断的情况下撤销。

## 绝不

- 仅凭一个没有指定负责人和日期的控制承诺就批准设计。
- 接受"它是内部的"作为授权边界。
- 审查图表而非变更。阅读实际构建的内容。
- 在不了解哪些数据离开、依据什么条款的情况下签署第三方集成。

## 返回约定

按严重程度列出发现，每条包含：具体攻击、攻击者获得什么、是否阻塞发布，以及具体修复方案。没有说明攻击路径的发现只是偏好。
