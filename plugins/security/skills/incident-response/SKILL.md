# 事件响应

> 数据泄露通报受法定时限约束，在若干司法管辖区以小时计。一旦可能涉及个人数据，立即让法务与风险团队及具备资质的律师介入——而不是等技术工作做完之后。

## 判定为事件，并明确宣布

代价最高的延误，是花一小时争论这到底算不算事件。尽早宣布；撤销一个已宣布的事件成本很低，而晚一小时才发现它是真的，代价高昂。

立即指定一名**事件指挥官**。一个人负责协调，不做技术工作。其他人各有明确职责。事件失败更多源于协调问题，而非技术能力不足。

## 行动顺序

**1. 先遏制，再调查。** 先止血：隔离主机、吊销凭据、禁用账户、封堵路径。观察攻击者以获取更多信息很诱人——只有在经过深思熟虑的决策后才这么做，不要默认如此。

**2. 遏制的同时保全证据。** 重建之前先做快照。在关机之前捕获易失状态——内存、连接、运行中的进程。重建被入侵的主机会销毁他们如何进入的唯一记录，而你会需要它。

**3. 确定范围。** 访问了什么、拿走了什么、何时开始、是否仍在进行。假定初始范围被低估了；通常确实如此。在宣布遏制完成之前，排查持久化机制和横向移动。

**4. 清除并恢复。** 移除访问权限、关闭路径，然后恢复。从已知良好的状态重建，而不是就地清理——你无法证明一台清理过的主机是干净的。

轮换攻击者可能接触到的所有凭据，而不只是你已知他们用过的那些。

**5. 恢复后持续监视。** 重新入侵很常见。针对他们使用的路径及其邻近路径进行专项监控。

## 沟通

维护一条时间线作为唯一事实来源，随事实确立而更新，每条记录都标注时间戳和来源。事件会快速产生相互矛盾的信息，时间线正是防止同一个问题被给出三种不同答案的关键。

说明已知什么、尚不知什么、下次更新在何时。在原因或范围确立之前，绝不要对外推测——撤回的声明会延长事件周期，对公信力的损害比事件本身更大。

## 事后

无责复盘，聚焦系统而非个人。有用的问题包括：本可以怎样更早发现，是什么导致遏制缓慢，我们缺少哪些本应具备的东西，以及最初是什么让这一切成为可能。

输出带负责人和日期的行动项。复盘若不产生承诺的变更就是走过场，同样的事件还会重演。

## 准备

计划本身不如演练过它重要。至少每年演练一次：针对现实场景的桌面推演能发现缺口——非工作时间谁有权限、凭据在哪里、谁联系律师——而此时发现这些缺口的成本为零。

## 来源

本技能的 `references/sources.md` 列出了解决此处问题的外部权威来源——每个来源在哪些方面具有权威性，以及你可以如何使用它。在回答其涵盖的任何问题之前先查阅它们，并注明你所使用的来源。大多数可免费阅读但不可免费复制；每个来源的使用说明具有约束力。

## 绝不

- 在捕获证据之前重建或擦除被入侵的主机。
- 让负责技术响应的人同时负责对外沟通。
- 在你能说明入侵是如何发生的且路径已关闭之前就关闭事件。
- 在事件未关闭期间，在响应渠道之外推测原因或归因。
