# 数据迁移

迁移被当作数据移动问题来估算，结果却是数据质量问题。传输是简单的部分；发现旧系统实际包含什么才是耗时所在。

## 映射之前先剖析源数据

看真实数据，不要看 Schema，也不要听别人说它包含什么。每个遗留系统都有名不副实的字段、本该是枚举却写成自由文本的地方、两个看起来都像正本的重复项，以及早于某条人人以为一直适用的规则的记录。

对你打算迁移的每个字段，统计不同值数量、空值率、格式差异和异常值。这是迁移中回报最高的单项活动，也是最常被跳过、转而直接开始映射的一项。

**决定哪些不迁移。** 全部迁移是默认做法，却很少是正确答案。把没有实际用途的归档，只迁移干净的子集——这能同时缩小映射、核对和切换窗口。

## 逐字段写下映射，包括难处理的部分

对每个目标字段：源字段、转换方式、源为空时怎么办、源不匹配时怎么办。最后一列决定了迁移的成败。

**无法干净映射的记录需要决策，而不是默认处理。** 一行被悄悄丢弃、必填字段填入占位符、或值被截断，都是几个月后才被信任该数字的人发现的缺陷。把异常路由到一份由人工逐条处理的清单，并统计数量。

## 在完整副本上演练，不止一次

在样本上演练只能证明映射能编译。在完整副本上演练才能验证耗时、发现病态记录，并给出切换窗口的真实数字。

预期要演练多次。每次都应以核对和缺陷清单收尾，最后一次应当干净且已计时。从未在生产数据量下完成过一次完整运行就进入切换，意味着切换就是第一次完整运行。

## 有意识地选择切换方式

- **大爆炸式**——停止、迁移、在新系统上启动。最容易推理，全部风险集中在一个窗口内。当窗口可承受且回滚真实可行时可用。
- **并行运行式**——两套系统同时运行，一套为权威。更安全，也昂贵得多，因为必须有东西让两者保持同步，还得有人每天核对差异。
- **分阶段式**——按实体、地区或业务单元。缩小影响范围，却制造了迁移中最难的问题：边界存在期间，记录会跨边界相互引用。

无论选哪种，都要指明不可逆点和该点两侧的回滚方案。**从未执行过的回滚不算回滚**，而且新系统接受实时写入后，回退意味着把这些写入合并回去——那是没人规划过的第二次迁移。

## 核对数量，也核对取值

仅靠行数只能发现加载被截断，别的什么都发现不了。对任何涉及财务的内容核对控制总数，对关键字段核对分布，并抽样逐条比对记录。然后让使用数据的人检查他们烂熟于心的记录——他们能发现任何查询都找不到的问题。

切换一周后再核对一次。取代迁移的持续集成中的问题，通常那时才浮现，而不是当天。

## 为长尾做规划

迁移被宣布完成后，还会持续数月产生问题。让源系统保持可读的时间比感觉需要的更长，保留映射和异常清单，并保留专人负责。否则，关于某条历史记录的问题将无人能答，因为旧系统已按计划退役。

## 绝不

- 从 Schema 而非数据出发做映射。
- 让记录映射失败后被丢弃，却不落到有人处理的清单上。
- 未经完成并核对过的全量演练就切换。
- 在核对窗口关闭前就退役源系统。
