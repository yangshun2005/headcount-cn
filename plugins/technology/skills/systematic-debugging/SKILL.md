# 系统化调试

## 规则

**原因未证实前，不许修复。** 让症状消失却给不出解释的改动，什么都没修好——它只是把故障挪到了你看不见的地方。

## 方法

1. **确定性地复现。** 不能按需触发，就不知道何时算修好。间歇性意味着你还没找到那个变量——顺序、时机、状态、环境、数据。
2. **缩小爆炸半径。** 二分排查：哪个提交、哪个输入、哪个分支、哪一层。每一步把搜索空间减半，而不是通读一切。
3. **提出一个可能被证伪的假设。** "写入后缓存返回了过期行"是假设。"缓存有问题"不是。
4. **直接检验假设**——一行日志、一个断点、一个探针。去证明，别去推断。
5. **解释整个症状。** 如果你的原因能解释报错，却解释不了它为什么从周二开始出现，那你找到的是*一个* bug，不是*那个* bug。
6. **修复，再用回退验证。** 把 bug 放回去，确认测试再次失败。这一步常被跳过，而它恰恰证明的是因果关系，不是巧合。

## 反模式

- **散弹式改动**——同时改好几处。这下你无法归因到底是哪处修好的。
- **"大概是偶发。"** 这不是诊断。间歇性失败的测试正在报告真实的竞态、顺序依赖或共享状态泄漏。
- **只修症状**——捕获异常、加重试、放宽超时——却不知道是谁抛出的。
- **轻信报错信息里的位置。** 它浮现的地方，很少是它起源的地方。

## 绝不

- 在没有"修复前失败、修复后通过"的复现用例时关闭 bug。
- 把改动部署到生产环境来验证它是否有效。先在能观察的地方复现。
- 在同一步里既改环境又改代码。
- 把调试辅助手段当作修复留在代码里——放宽的超时、禁用的检查、被吞掉的异常。

## 交付约定

说明复现方式、已证实的原因、修复方案，以及证明该修复正是针对此原因的验证。列出你排除了哪些可能，以及如何排除的。
