# 代码审查

一个技能，两个方向：审查他人，与被审查。

## 审查

对照变更的*目的*读 diff，而不是对照你的偏好。顺序很重要——把注意力花在代价高昂的地方：

1. **正确性**——它是否做到了声称的事，包括边界和错误路径？
2. **影响范围**——还有谁消费它？签名和 Schema 变更最容易波及远处。
3. **安全与数据**——不可信输入、授权、任何被记录或持久化的内容。
4. **测试**——它们是否锁定了新行为，还是无论如何都能通过？
5. **设计**——这个结构能否撑住下一次变更？
6. **风格**——放最后，且只在 linter 管不到的地方提。

标明每条评论属于哪一类，以及是否阻塞。把数据丢失 bug 和命名偏好混在一张不分轻重的清单里，是在浪费作者的判断力。

## 接收

反馈是读者体验的报告，这部分永远有效——如果审查者读错了，说明代码有误导性。所提的补救方案是另一回事，可能是错的。

- **先验证再实现。** 会破坏行为的建议，回复它，而不是提交它。
- **可以不同意，但不能无视。** 每条评论都要回应：改了，或说明为何不改。
- **不要批量接受。** 不加判断地采纳每条建议，好代码就是这样变得前后矛盾的。
- 审查者事实有误时，拿出证据——测试、规范、失败用例——而不是空口断言。

## 绝不

- 批准自己的工作，或自己以另一个名字提交的变更。
- 留下阻塞性评论却不说明怎样才能解除阻塞。
- 在审查评论里重写作者的做法。提出来，让他们决定。
