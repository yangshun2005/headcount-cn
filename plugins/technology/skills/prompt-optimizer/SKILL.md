# 提示词优化器

## 先诊断，再改写

糟糕的输出只有少数几种原因，修复方式因原因而异：

- **描述不足**——模型在猜测你知道的信息。最常见。
- **描述过度**——约束太多且相互冲突，模型随意满足其中一部分。
- **形态错误**——想要表格却要求段落，想要选项却要求决策。
- **没有成功标准**——提示词没说什么是好，质量便无从保证。
- **指令被埋没**——真正的任务夹在上下文中间，被当作上下文对待。
- **确实困难**——任务需要模型没有的信息，任何提示词都无济于事。直接说明，不要反复迭代。

改写前先读实际的糟糕输出。失败模式会指出原因。

## 确实有效的方法

- **说该做什么，而非不该做什么。** 否定指令比肯定指令弱，还常常招来所命名的东西。
- **给出输出形态**——章节、长度、格式。格式重要就展示示例，而非描述。
- **任务依赖判断时，提供一个完整示例。** 示例每 token 承载的指令多于描述，一个好示例胜过三个平庸的。
- **说明受众和目的。** "写给正在决定是否采用此方案的技术读者"比大多数形容词更能改变输出。
- **分析类任务先要推理再要答案**——顺序很重要，先给出的结论会被辩护而非推导。
- **给出退路。** 告诉它输入不足时该怎么做，否则它会编造。

## 无效的方法

礼貌、威胁、激励、强调重要性、堆砌最高级。这些消耗 token，收效甚微。用三种措辞重复同一指令也一样——这通常说明指令本身不清楚，而非起到强化作用。

## 结构

任务放最前，上下文其次，输出格式放最后，最靠近生成位置。指令与输出之间的长上下文正是指令容易丢失的地方。

重复使用的提示词，要把固定指令与可变输入明确分开，让模型能分辨。

## 测试

一次运行看起来好，不代表提示词完成。同一输入跑三到五次，看方差——那才是真实质量。再用刁钻输入测试：空、过长、模糊、对抗性。

修最差情况，而非平均情况。平均是你在测试中看到的，最差是用户看到的。

## 生成变体

提示词重要到值得优化时，要产出真正不同的版本，而非同一措辞的变体：

- **简洁版**——只有指令，最少框架。往往表现最好，且最便宜。
- **结构化版**——明确章节、编号约束、定义输出形态。
- **示例主导版**——一个完整示例承载大部分指令。
- **角色框定版**——任务前先设定受众和立场。

四种版本在同一输入上测试。哪个胜出很难预测，"提示词越长越好"的直觉对错各半。

## 评分输出

用看到结果前写好的标准评判，否则你会为任何返回结果找理由。多数任务看：是否完成任务、是否正确、形态和长度是否合适、是否无需编辑即可使用。每次运行单独评分，而非形成整体印象——印象会被最好的一次主导，而最差的一次才重要。

## 跨模型迁移

不要假设提示词能直接迁移。模型在系统指令与用户指令的权重、长上下文处理、格式响应上各不相同。在目标模型上重新测试，尤其警惕经过多次小迭代调优的提示词——它们往往拟合了某个模型的怪癖。

## 绝不

- 未读失败输出就改写提示词。你会修错地方。
- 测试运行之间改动超过一处。
- 凭单次输出判断改动。采样方差会骗你。
- 因为某条指令原本就在就保留它。每一行都要挣得自己的 token。
