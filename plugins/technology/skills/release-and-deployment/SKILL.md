# 发布与部署

发布风险主要由批次大小决定。大型低频发布很危险，因为许多变更同时上线，没人能判断是哪个出了问题——于是团队发布更少，每次发布就更大。这个循环本身就是问题。

## 将部署与发布分离

部署代码和向用户暴露行为是两种不同的动作，把它们耦合在一起会迫使每次部署都成为业务决策。

用功能标志解耦：持续部署，审慎暴露。这样回滚就变成配置变更而非重新部署，在最糟糕的时刻，这是秒级和分钟级的区别。

功能标志是库存，也会腐烂。给每个标志指定负责人和移除日期；满是陈旧标志的代码库有没人测试过的组合状态。

## 流水线是质量门禁

自动化提交到生产之间的所有环节，让流水线来拒绝。手动步骤在压力下会被跳过，而那恰恰是它们最重要的时候。

门禁按从快到慢排序，让失败代价低廉：先 lint 和单元测试，再集成测试，最后是需要已部署环境的任何检查。慢到会被绕过的流水线，比检查更少但更快的流水线更糟，因为它一定会被绕过。

只构建一次，将同一构建产物在各环境中晋级。按环境重新构建意味着你测试的东西不是你发布的东西。

## 逐步推出

先暴露给小部分人群，观察真实信号后再扩大。金丝雀或按比例推出能把全面故障变成受控故障。

在开始**之前**定义中止条件，包括阈值和指定的决策人。在压力下、变更还新鲜时，本能总是再等一会儿看看。

## 数据库变更是不对称风险

代码可以回滚；数据不能。让 Schema 变更向后兼容且分多步：添加新结构，双写，迁移，切换读取，然后移除旧结构——全程应用需容忍两种形态。

用生产规模的数据测试迁移。在开发数据集上瞬间完成的迁移，可能把大表锁住一段没人建模过的时间。

## 工具

流水线：GitHub Actions、GitLab CI、CircleCI、Buildkite、Jenkins 等。

持续交付和渐进式推出：Argo CD、Flux、Spinnaker 等；用于解耦部署与发布的功能标志——LaunchDarkly、Unleash、Split 等。

Schema 迁移：Flyway、Liquibase、Alembic 等。无论用哪个，关键特性是迁移被版本化、有序，并由流水线应用，而不是由人拿着数据库客户端执行。

## 绝不

- 将部署代码与暴露行为耦合。
- 晋级与测试过的不同的构建产物。
- 在没有定义中止条件的情况下开始推出。
- 发布需要应用和数据库同时部署的 Schema 变更。
