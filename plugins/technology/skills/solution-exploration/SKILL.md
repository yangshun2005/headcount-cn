# 方案探索

最昂贵的 bug 是决策，不是缺陷。这一步在实现之前进行，而不是替代实现。

## 弄清真正想要什么

提出的请求是一个披着需求外衣的方案。要挖到它下面：

- 对方想要什么结果？没有它今天会坏掉什么？
- 还有谁碰这块，他们现在对它有什么假设？
- 明确**不**要求的是什么？
- 怎么知道它成了——可观察到的差异。

如果答案互相冲突，先停下来解决冲突。按两个需求的平均值来构建，两边都不满足。

## 生成真正不同的选项

同一想法的两个变体只是一个选项。强制拉开真正的范围：

- 能起作用的最小方案。
- 假设下季度范围翻倍的版本。
- 不需要任何新活动部件的版本。
- 买、借，或什么都不做。

对每个选项：代价是什么，排除了什么，以及它成立必须满足什么条件。

## 收敛

推荐一个，并说明其他为什么落选。没有推荐结论的对比只是推动了工作，没有完成工作。

指出该推荐最依赖的假设——如果计划会崩，就崩在这里。

## 绝不

- 摆出你自己都不会接受的选项，只为给你想要的那个当陪衬。
- 因为任务"很简单"就跳过这一步。简单任务在这里花五分钟。
- 让偏好冒充理由。
