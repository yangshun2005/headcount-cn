# Skill 编写

一个 skill 会被评判两次：是否在恰当时机加载，以及加载后是否有帮助。大多数都栽在第一关。

## 描述负责触发

决定是否加载时，只读描述。就为这件事写：

- 先用一句话说明 **skill 做什么**。
- 再说明 **何时该用它** —— 具体情境，用人们实际会说的措辞，包括间接说法（"为什么这个转化不了"和"CRO 审计"都算）。
- 点明 **仍应触发它的边缘情况**，必要时也说明什么 *不该* 触发。

描述含糊会同时导致两种失败：该命中的情况没命中，帮不上忙的情况却触发了。

## 正文负责干活

写给一个有能力、但今天还没想过这个问题的人。这意味着：

- **方法胜过说教。**"要彻底"是噪音。有序的步骤才是指令。
- **说明每条规则背后的失败。** 没有失败案例支撑的规则会被下一个读者优化掉。
- **具体到可能出错。** 含糊到无法反驳的指导，也模糊到无法遵循。
- **长材料放进 `references/`**，并说明何时去读。正文应能装进工作记忆。

## 重叠是沉默的杀手

两个 skill 的描述都能匹配同一请求，意味着谁都不能可靠胜出。添加新 skill 前，先查清已有内容覆盖了哪些领域。优先扩展现有 skill，或把同族合并为一个带 references 的 skill，而不是添加一个近邻。

## 机制

- `name` 必须是小写连字符格式，且与目录名一致，否则 skill 不会加载。
- 一个 skill 一个目录，`SKILL.md` 放在根目录；辅助材料放在 `references/` 和 `scripts/`。

## 发布前验证

写三个应触发它的请求和两个不应触发的请求，检查描述是否真能区分。如果某个近似请求会把它拉进来，就收紧描述。

## 来源

本 skill 的 `references/sources.md` 列出了解决此处问题的外部权威 —— 每个权威的适用范围，以及你可以如何使用。回答它们覆盖的任何内容前先查阅，并注明所用来源。多数可免费阅读，但不可免费复制；每条的用途说明具有约束力。

## 绝不

- 发布描述未说明何时使用的 skill。从不触发的 skill 是累赘。
- 写一个只是复述模型无需提示就已做得很好的 skill。
- 让两个 skill 声称同一触发条件。要么划清边界，要么合并。
- 未针对促使你编写它的那个案例运行过 skill 就发布。
