# API 设计

API 是一旦有人依赖就无法收回的承诺。设计时务必牢记：设计错误的代价由每个集成方持续承担。

## 建模领域，而非数据库

暴露使用者思维中的概念。照搬内部表结构的接口会泄露实现细节，存储一变就崩，还迫使使用者重建你本已拥有的语义。

用领域自身的命名来命名。命名、大小写、日期格式和标识符风格的一致性，比任何单项选择是否最优都重要——统一不完美的接口可学，不一致的卓越接口不可学。

## 错误是契约的一部分

大多数集成的代码大部分都花在失败处理上。给失败路径与成功路径同样的重视：

- **区分机器可读的错误码与人类可读的消息。** 使用者根据错误码分支；消息供开发者读日志。
- **说明该怎么办。** 是否可重试，以及多久之后重试。
- **绝不泄露内部信息**——错误体里的堆栈跟踪和 SQL 既是安全问题，也是糟糕设计。
- **明确哪些失败对应哪个状态码。** 校验、授权和冲突是不同情况，绝不应共用同一形态。

## 兼容性

新增可选字段是安全的。删除字段、重命名字段、收紧校验、更改默认值或新增必填参数都属于破坏性变更，其中后三项会破坏那些本没有做错任何事的使用者。

必须破坏时再做版本管理，并明确旧版本存活多久。没有日期的弃用等于没人会行动的弃用。

尽可能用扩展代替版本管理：新增可选字段对使用者零成本，新版本则要他们做迁移。

## 分页、过滤与限制

任何可能增长的数据集合从首个版本起就需要分页——事后补加对每个使用者都是破坏性变更。对读取期间会变化的数据，优先用游标而非偏移量；并发写入下偏移量分页会静默跳过和重复记录。

在契约中写明速率限制，并在响应中传达。未文档化的限制会在使用者的生产事故中被发现。

## 来源

本技能的 `references/sources.md` 列出了解决此处问题的外部权威——每个权威的适用范围，以及你可以如何使用。回答其覆盖的任何问题前先查阅，并注明所用来源。多数可免费阅读但不可免费复制；每条的使用说明具有约束力。

## 工具

规范与文档：OpenAPI 配合 Redocly、Stoplight 或 Scalar；使用者为内部服务时用 gRPC 配合 protocol buffers，等等。

设计评审与测试：Postman、Insomnia、Bruno 等。契约测试——Pact 等——能在使用者之前捕获破坏性变更。

从规范生成文档，从代码或与代码并行生成规范。手工维护的 API 文档在一个发布周期内就会出错，而自信地出错比缺失对使用者更糟。

## 绝不

- 通过接口暴露内部标识符或存储结构。
- 返回含义需从消息文本推断的错误。
- 收紧现有端点的校验却称之为非破坏性。
- 发布没有分页的集合端点。
